## Actual boundaries and changes

`mcp/batch_adapters.rs::run_batch` already accepts one root in the shared registry. `run_batch_accepted` prepares ordered input, reserves/resumes the parent on a blocking worker, awaits existing derived completion, dispatches each pending child, optionally finalizes a rejected child on another worker, completes publication and reconciles final progress on a blocking reader. Actual MCP `store_memories`/`forget_memories` dispatch and daemon `mutate_batch` consume this implementation. PR165's real stdio/socket roots already continue through serialization/write/flush.

Reuse `performance::{measure,Worker,Timer,Hold,Timeline,event}` and the existing root sampling decision. A direct typed-adapter control can create its own diagnostic root, but a transported batch must inherit the already selected root; no per-item decisions or sampling counters. New fixed operation/stage labels describe batch work, not caller payloads or operation IDs. No parallel observer/readiness authority.

| Producer / proposed touch | Facts and precise unit |
| --- | --- |
| `run_batch` and existing accepted path | Batch kind and supplied item count, preparation outcome, duration, returned parent reservation state, item status totals, returned ready flags and retained receipt inventories. These are selected-call/result facts, not inferred global completed work or a new barrier. A returned result may retain commits from a prior attempt. |
| Reservation worker | `Worker` context/queue, existing storage read-lock wait/hold, actual reserve/resume call duration and typed result. Returned parent receipt's `replayed` bit distinguishes known fresh reservation from replay; explicit unknown remains unknown. Never read back an unsafe handle to convert ambiguity to success. |
| Actual child dispatch | Attempt event only for a currently pending child actually dispatched; returned successful/committed-unready/unknown/rejected/provider-unavailable outcome at the existing branch. A skipped completed child is replayed inventory, not another attempt or commit. Counts are separated from the parent and from bookkeeping. Existing single-store insertion/explicit-sync hooks remain the only hooks for their underlying physical work. |
| Rejected-child bookkeeping worker | Context/queue/lock/call result. A concurrent canonical child result still wins exactly as before. Returned bookkeeping inventory is not automatically a count of new commits. If finalization is unknown, retain unknown and the existing operation identity without emitting it as a metric label. |
| Final progress worker | Context/queue and existing read-lock/call duration. Reconcile only where the existing healthy-handle branch permits it. Instrumentation creates no work ticket or readiness proof absent in the original implementation; root cancellation still cannot imply drained work. |
| `storage/metadata/batch.rs::commit_batch` | Reuse existing `commit_call` vocabulary at the one actual `tx.commit()` boundary, with bounded resource `batch_reservation` or `batch_rejection` from the already supplied typed receipt outcome. Count call attempt/return, not guessed backend syncs. Preserve injected ambiguity and guard/drop/error ordering: a raw commit-call success can coexist with caller-visible unknown. Ordinary child record/effect commits already have their actual hook from165; do not add a second child commit hook at the caller. |
| Actual stdio and daemon output | Reuse165's production `serve_io` and connection handler, actual encoded byte counts/flush outcome. A batch can have committed parent/children even if delivery fails. No change to framing, public schema, transport cap or fallback behavior. |

Uninstrumented provider-internal/backend work remains unknown. File/sync wrappers remain counted once at their actual existing call site; do not add a second “batch sync” count. Parent duration includes child time, lock wait and sink time: retain nesting and top-level residual rather than summing them. When useful, scalar result totals can be counted during existing iterations; any diagnostic-only traversal must be gated by `enabled()` and bounded by the already validated batch size. Disabled/unsampled paths must not create trace state, evaluate payload-derived labels, sample clocks or allocate new instrumentation state.
